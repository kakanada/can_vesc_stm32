# Протокол моста VESC Tool ↔ CAN (vesc_bridge)

Техническая изнанка `vesc_bridge.h`/`vesc_bridge.c`: точные байтовые форматы протокола, чтобы не
пришлось второй раз лазить в исходники прошивки VESC при отладке или доработке. Для пошагового
практического руководства (конфигурация, интеграция, безопасность, тестирование) — см.
[VESC_EXPRESS_GUIDE.md](VESC_EXPRESS_GUIDE.md).

Все форматы ниже сверены с исходным кодом прошивки VESC (репозиторий
[vedderb/bldc](https://github.com/vedderb/bldc)): `comm/comm_can.c`, `comm/commands.c`,
`comm/packet.c`, `datatypes.h`, а также `crc.c` (через
[vedderb/nrf51_vesc](https://github.com/vedderb/nrf51_vesc), тот же алгоритм) — см. §8.

## 1. Общая идея моста

VESC Tool умеет говорить с "хабом" (обычно это сама VESC, к которой ПК подключен напрямую по
USB/UART, либо VESC Express по WiFi/TCP) и через него адресовать команды **другим** VESC на той же
CAN-шине, которых ПК физически не видит. Хаб для этого:
1. Разбирает внешнее кадрирование протокола VESC Tool (пришедшее по USB/UART/TCP/вообще любому
   байтовому каналу).
2. Если payload начинается с `COMM_FORWARD_CAN` — достаёт целевой CAN ID и вложенную команду,
   форвардит её конкретной веске по CAN через штатный механизм многокадровой сборки
   (`CAN_PACKET_FILL_RX_BUFFER[_LONG]` + `CAN_PACKET_PROCESS_[SHORT_]BUFFER`).
3. Ответ, который веска-цель пришлёт по той же CAN-механике, пересобирает и отправляет обратно ПК
   тем же внешним кадрированием, **без** повторной обёртки в `COMM_FORWARD_CAN`.
4. Небольшой набор команд хаб обрабатывает **локально**, не форвардя на CAN (см. §5) — иначе VESC
   Tool не сможет даже "поздороваться" с хабом.

`vesc_bridge` реализует шаги 1-4 независимо от того, какой транспорт принёс байты (TCP-сокет, UART,
USB CDC) — не трогает сам транспорт, только скармливание/выдача сырых байт через два универсальных
колбэка (`VESC_Bridge_FeedBytes` / `tx_callback`). Форвардинг по CAN использует `CANMGR_Send()`
(`can_manager.h`, проект `can-managers-stm32`) напрямую — `vesc_bridge` независимый потребитель
`can_manager`, регистрирующий собственные фильтры приёма (см. §3 "Собственный CAN ID моста" и §6
ниже за деталями), а не проходит через `motor_vesc.h`.

## 2. Внешнее кадрирование (packet.c) — байт-поток ↔ пакет

```
короткий (payload ≤ 255 байт):
  [0x02][len:1 байт][payload: len байт][crc_hi][crc_lo][0x03]

средний (payload 256..65535 байт):
  [0x03][len_hi][len_lo][payload: len байт][crc_hi][crc_lo][0x03]
```

- CRC считается ТОЛЬКО по `payload` (не по старт-байту/длине/стоп-байту).
- Длинный вариант (3-байтная длина, старт-байт 0x04, до 16 МБ payload — под обновление прошивки) не
  реализован — см. §7.
- `vesc_bridge` умеет и принимать, и отправлять оба реализованных формата — короткий выбирается
  автоматически, если `len ≤ 255`, иначе средний.

### CRC16 (XMODEM)

```c
unsigned short crc16(unsigned char *buf, unsigned int len) {
    unsigned int i;
    unsigned short cksum = 0;                 /* init = 0x0000 */
    for (i = 0; i < len; i++) {
        cksum = crc16_tab[(((cksum >> 8) ^ *buf++) & 0xFF)] ^ (cksum << 8);
    }
    return cksum;
}
```

Стандартный **CRC-16/XMODEM** (poly `0x1021`, init `0x0000`, без рефлексии, без финального XOR). В
`vesc_bridge.c` реализован побитово (без 256-элементной таблицы) — математически идентичный
результат:

```c
crc ^= (byte << 8);
for (8 раз) { crc = (crc & 0x8000) ? (crc << 1) ^ 0x1021 : (crc << 1); }
```

Проверено на общепринятом контрольном векторе: CRC-16/XMODEM("123456789") = `0x31C3`.

## 3. Многокадровая пересылка по CAN (comm_can.c)

Все CAN ID здесь — Extended, формат `(cmd_id << 8) | целевой_vesc_id`, как и у всего остального в
этой библиотеке.

### Коды команд (из `datatypes.h`, `CAN_PACKET_ID`)

| Имя | Код |
|---|---|
| `CAN_PACKET_FILL_RX_BUFFER` | 5 |
| `CAN_PACKET_FILL_RX_BUFFER_LONG` | 6 |
| `CAN_PACKET_PROCESS_RX_BUFFER` | 7 |
| `CAN_PACKET_PROCESS_SHORT_BUFFER` | 8 |

(Уже присутствуют в `motor_vesc.h` как часть `VESC_CAN_PacketId_t`.)

### Короткий путь — payload вложенной команды ≤ 6 байт

Один кадр `CAN_PACKET_PROCESS_SHORT_BUFFER`, payload (8 байт):
```
[0]  reply_to_id   - CAN ID отправителя (для нас - own_can_id моста)
[1]  send_flag     - см. §4
[2:] вложенная команда, как есть, до 6 байт
```

### Длинный путь — payload вложенной команды > 6 байт

1. `CAN_PACKET_FILL_RX_BUFFER` — по 7 байт данных за кадр, offset 1 байтом (0..255):
   ```
   [0] offset (0..255)
   [1:] до 7 байт данных
   ```
2. Для данных дальше 255-го байта — `CAN_PACKET_FILL_RX_BUFFER_LONG`, по 6 байт данных за кадр,
   offset 2 байтами (big-endian, 0..65535):
   ```
   [0] offset_hi
   [1] offset_lo
   [2:] до 6 байт данных
   ```
3. Завершающий кадр `CAN_PACKET_PROCESS_RX_BUFFER` (payload ровно 6 байт):
   ```
   [0] reply_to_id  - CAN ID отправителя (own_can_id моста)
   [1] send_flag    - см. §4
   [2] len_hi        - длина ВСЕГО собранного payload, big-endian
   [3] len_lo
   [4] crc_hi        - CRC16(payload) всего собранного буфера, big-endian
   [5] crc_lo
   ```
Получатель проверяет CRC над накопленным буфером на офсетах `0..len` и только при совпадении
исполняет команду.

Та же механика используется и в обратную сторону — ответ вески-цели пересобирается точно так же
(`VESC_Bridge_OnCanFrame()` в vesc_bridge.c): `FILL_RX_BUFFER[_LONG]` копируют кусок в буфер
пересборки по офсету, `PROCESS_RX_BUFFER`/`PROCESS_SHORT_BUFFER` завершают приём (с проверкой CRC
для длинного варианта) и передают готовый ответ клиенту.

### Очередь форвардинга и fire-and-forget (v1.11 → v1.12)

**v1.11, найдено тестированием с реальным VESC Tool**: VESC Tool конвейерит запросы — например при
записи Motor Settings шлёт `SET_MCCONF` (форвардинг, ~491 байт, ~70 кадров чанками) и СРАЗУ ЖЕ, не
дожидаясь ACK, следом `GET_MCCONF` для read-back. До версии 1.11 у моста был ОДИН слот активного
форвардинга (`forward_src`/`forward_phase`), и новый `COMM_FORWARD_CAN` безусловно перезаписывал ещё
не отправленный старый ("последний побеждает") — `GET_MCCONF` затирал состояние `SET_MCCONF` раньше,
чем тот успевал полностью уйти на шину, поэтому ACK на `SET` не приходил никогда и запись в веску
реально не происходила. v1.11 завела FIFO-очередь, но следующий запрос всё ещё стартовал только
ПОСЛЕ ответа вески на предыдущий (или таймаута) — следующая, более серьёзная проблема.

**v1.12, снова найдено тестированием с реальным VESC Tool**: VESC Tool шлёт `COMM_ALIVE`/`SET_CURRENT`
и т.п. с частотой до десятков Гц, НЕ дожидаясь ответа вообще (большинство этих команд веска даже не
подтверждает) — модель 1.11 "следующий после ответа" душила это насмерть: 20 команд
`COMM_ALIVE`/`SET_CURRENT` подряд + `GET_VALUES` отвечали через ~2 секунды вместо немедленно, т.к.
каждая команда без ответа ждала полный `VESC_BRIDGE_FORWARD_TIMEOUT_MS`. Сверка с исходником
`vedderb/vesc_express` (`commands.c`) подтвердила: настоящий Express на `COMM_FORWARD_CAN` делает
ровно `comm_can_send_buffer()` и возвращается немедленно — ответы (если будут) приходят полностью
АСИНХРОННО, отдельными CAN-кадрами, никак не блокируя отправку следующей команды.

С 1.12 `vesc_bridge_forward_step()` переведён на честный fire-and-forget: запрос считается
завершённым, КАК ТОЛЬКО все его CAN-кадры фактически ушли в `can_manager` (`CANMGR_Send()` вернул
`HAL_OK`) — фаза `VESC_BRIDGE_FWD_WAITING` и завязанный на неё `VESC_BRIDGE_FORWARD_TIMEOUT_MS` для
старта следующего запроса убраны полностью; `VESC_Bridge_OnCanFrame()` (приём ответа) больше НИКАК не
взаимодействует с состоянием отправки — ответ на запрос N может прийти когда угодно (или не прийти
вовсе) и не влияет на запрос N+1. `VESC_BRIDGE_FORWARD_TIMEOUT_MS` сохранён только для
`VESC_Bridge_IsTargetActive()` (см. ниже).

Очередь (кольцевой байтовый буфер, `VESC_BRIDGE_FORWARD_QUEUE_BYTES`, по умолчанию 4096 байт - см.
`vesc_bridge.h`) тоже переделана под реальный темп: вместо фиксированного числа слотов по
`VESC_BRIDGE_MAX_PAYLOAD` байт каждый (дорого и мало по счёту одновременно) — записи переменной
длины `[target_id:1][len:2][payload:len]`, типичная команда (`COMM_ALIVE`, `SET_CURRENT` и т.п.) -
единицы байт, поэтому при 4096 влезает одновременно и пара десятков мелких команд, и один-два больших
конфигурационных пакета. Переполнение (`VESC_Bridge_GetForwardQueueOverflowCount()`) — НОВЫЙ запрос
ПОЛНОСТЬЮ ОТБРАСЫВАЕТСЯ, уже стоящие в очереди не трогаются (в 1.11 было наоборот — "последний
побеждает" перезаписывал хвост очереди).

### Собственный CAN ID моста (`own_can_id`)

Чтобы веска-цель знала, куда слать ответ (`reply_to_id` в кадрах выше), мост обязан иметь свой CAN
ID на шине. Это поле конфигурации (`VESC_Bridge_Config_t.own_can_id`) — назначается вручную и должно
быть уникальным на шине: не совпадать ни с одной реальной веской и ни с одним другим
мостом/устройством (библиотека это не проверяет, аналогично `position_memory_backup_index` в
`motor_vesc.h`).

### Регистрация фильтров приёма в `can_manager`

`VESC_Bridge_Init()` регистрирует 4 фильтра — по одному на каждый из cmd_id 5/6/7/8 выше — с ТОЧНЫМ
(exact-match) совпадением `id = (cmd_id<<8)|own_can_id`, маска `0x1FFFFFFF` (все 29 бит Extended
ID), а НЕ широкий фильтр `mask=0xFF00` (любой `vesc_id`, как у штатных статусов `motor_vesc.h`).
Ответ от вески-цели всегда адресуется `reply_to_id = own_can_id` (см. `[0] reply_to_id` в форматах
кадров выше) — конкретному значению этого моста, а не произвольному ID в диапазоне, поэтому точный
фильтр корректно описывает реальную адресацию (подробное обоснование выбора —
Техническое_задание.md этого проекта, вне `git/`). `VESC_Bridge_OnCanFrame()` дополнительно сверяет
`id == own_can_id` сама — это теперь defense-in-depth (на случай вызова в обход `can_manager`), а не
единственная линия защиты.

## 4. Поле `send`/`commands_send` при форвардинге

При форвардинге `vesc_bridge` всегда передаёт `send_flag = 0` (константа `VESC_BRIDGE_SEND_FLAG` в
`vesc_bridge.c`) — это то же значение, которое использует официальный обработчик `COMM_FORWARD_CAN`
в прошивке VESC (`comm_can_send_buffer(data[0], data + 1, len - 1, 0)`), и единственное значение,
для которого подтверждено, что получатель корректно запоминает адрес возврата (`rx_buffer_last_id`)
для последующего ответа.

Если после тестирования какие-то конкретные команды не получают ответа через мост — это первое место
для проверки.

## 5. Локальные команды (обрабатываются мостом сам, не форвардятся)

Если `payload[0]` (COMM_PACKET_ID) не равен `COMM_FORWARD_CAN` — команда адресована самому мосту, а
не веске за ним.

### `COMM_FW_VERSION` (код 0)

VESC Tool шлёт это при подключении к любому устройству для хэндшейка/определения совместимости.
Поля берутся из `VESC_Bridge_Config_t` (major/minor, `hw_name`, `fw_name`, `uuid12`,
`custom_config_num`) — не зашиты намертво, можно подстроить без правки библиотеки.

**[v1.9] `hw_type` — критичное поле для сценария "хаб без своего мотора".** Подтверждено на реальном
железе (VESC Tool 7.00, сессия тестирования библиотеки, до этой правки): со значением по умолчанию
`VESC_BRIDGE_HW_TYPE_VESC` (0, оставлено для обратной совместимости со старым поведением до v1.9)
VESC Tool считает мост ОБЫЧНОЙ веской и пытается прочитать MCCONF/APPCONF МОТОРА у самого моста
(`COMM_GET_MCCONF`/`COMM_GET_APPCONF` как локальные команды, не форвардинг) — мост на них не отвечает
(см. "Остальные локальные команды" ниже), UI мотора остаётся пустым/в ошибке, и до реальной вески за
мостом (вкладка CAN Fwd) пользователь фактически не добирается интуитивно. **Для хаба указывайте
`hw_type = VESC_BRIDGE_HW_TYPE_CUSTOM_MODULE`** (ровно то значение, которым представляется настоящий
VESC Express) — см. @warning у `VESC_Bridge_HwType_t` в `vesc_bridge.h`. Сама правка (hw_type/uuid12/
custom_config_num/fw_name конфигурируемые, активный скан для COMM_PING_CAN ниже) на реальном VESC
Tool ЕЩЁ НЕ проверена — см. §7.

UUID — 12 нулевых байт по умолчанию (как и до v1.9), либо `config->uuid12`, если задан (библиотека
сама не читает уникальный ID МК — не хардкодит `HAL_GetUIDwX`, специфичный для конкретной серии,
ради переносимости, см. `vesc_bridge.h`). Ненулевой уникальный UUID рекомендуется, если у вас
несколько мостов/устройств на связи одновременно.

### `COMM_PING_CAN` (код 62)

**[v1.9] Переписан на активный скан шины**, как и в прошивке VESC Express (`comm_can_ping` по всем
ID) — раньше отвечал только списком весок, уже зарегистрированных в `motor_vesc.c` через
`VESC_CAN_Init()`, из-за чего реальные вески на шине, которых вызывающий код не зарегистрировал
(частый случай — хаб как "прозрачная труба", без собственного учёта весок), не попадали в
автообнаружение VESC Tool вообще. Теперь `VESC_Bridge_Tick()` рассылает `CAN_PACKET_PING` на все ID
`0..254` (кроме `own_can_id`), порциями по `VESC_BRIDGE_SCAN_PINGS_PER_TICK` за тик (не забивая
очередь `can_manager` разом), собирает `CAN_PACKET_PONG` в течение `VESC_BRIDGE_SCAN_SETTLE_MS`
после последнего PING и только тогда шлёт VESC Tool итоговый список — полностью асинхронно, не
блокируя `VESC_Bridge_Tick()`. Не зависит от `motor_vesc.c`/`VESC_CAN_Init()` вообще — работает даже
если вызывающий код ни одной веской через `motor_vesc` не управляет, только форвардит.

### `COMM_LISP_READ_CODE` (130) / `COMM_GET_QML_UI_APP` (118)

**[v1.12]** VESC Tool шлёт эти при открытии вкладок Lisp/QMLUI — байты ответа для случая "скрипта
нет" сверены ДОСЛОВНО с исходником `vedderb/vesc_express` (`commands.c`, тестовой сессией): ровно 9
байт `[packet_id][total_size: int32 BE = 0][offset: int32 BE = 0]`. Без этого ответа VESC Tool ждёт
таймаут при каждом открытии этих вкладок, даже когда Lisp/QMLUI не используются вовсе. `total_size=0`
означает "кода нет" — так настоящий Express отвечает, когда запрошенный диапазон (`offset+len`)
превышает реальный размер (0, если скрипта нет).

### `COMM_GET_QML_UI_HW` (117) и прочие неизвестные локальные команды — молчание

**[v1.12]** Подтверждено исходником Express: `default: break` — ВСЕ нераспознанные команды (включая
`COMM_GET_STATS`=128, `COMM_LISP_GET_STATS`=134 и т.п.) игнорируются БЕЗ ответа. То, что мост молчит
на них — это НЕ пробел, а точное соответствие поведению настоящего Express; VESC Tool относится к
такому молчанию как к "функция недоступна" и просто не показывает соответствующий UI, не блокируя
остальную работу. Точка расширения `VESC_Bridge_OnLocalCommand()` вызывается для любого такого
нераспознанного локального payload — переопределяемая слабая функция, по умолчанию тоже ничего не
делает; добавляйте в неё обработку конкретных кодов, только если проверили точный формат ответа (см.
принцип выше — байты не угадывались, а сверялись с прошивкой).

### `COMM_CAN_FWD_FRAME` (33)

**[v1.12]** "Сырая" отправка одного CAN-кадра по явно заданным ID/`is_extended`, в обход
`(cmd_id<<8)|vesc_id` адресации остального протокола — использует VESC Tool для отладки/
CAN-анализатора. Формат payload (сверен с `comm_can_transmit_eid`/`sid` в прошивке Express):
```
[0..3] CAN ID, big-endian
[4]    is_extended (0/1)
[5:]   данные кадра, 0..8 байт
```
Отправляется напрямую через `CANMGR_Send()`, без ответа — как и в прошивке.

## 6. Зависимость от `can_manager` (было: `motor_vesc.h`)

До миграции на `can_manager` мост получал ответные CAN-кадры через `motor_vesc.h`: вызывающий код
сам звал `VESC_Bridge_OnCanFrame()` из своей реализации слабой функции
`VESC_CAN_OnForeignFrame()`, а исходящие кадры форвардинга мост отправлял примитивом
`VESC_CAN_SendRawFrame()`. Оба этих входа в
`motor_vesc.h` удалены (см. `Честные ограничения` в README.md motor_vesc) — мост теперь сам,
независимо от `motor_vesc`, регистрирует свои фильтры в `can_manager` (см. §3 выше) и отправляет
через `CANMGR_Send()`. `VESC_Bridge_Config_t.hcan` переименован в `bus`, тип — `CANMGR_Handle_t*`
(было `VESC_CAN_HandleTypeDef*`). Если у вас есть код, вызывавший `VESC_Bridge_OnCanFrame()` вручную
из `VESC_CAN_OnForeignFrame()` — этот вызов больше не нужен и не будет компилироваться (функция
удалена), достаточно один раз обновить `VESC_Bridge_Config_t` на новое поле `bus`.

- **Обновление прошивки весок через мост проверено на реальном VESC Tool 7.00** (веска hw 410,
  fw 7.0; STM32H743, FDCAN 500 кбит/с, AutoRetransmission=ENABLE, vesc_bridge 1.13, TCP 65102 поверх
  usb_eth): прошивка веск через хаб прошла успешно, веска после этого работает.
  `COMM_WRITE_NEW_APP_DATA`/`COMM_ERASE_NEW_APP` форвардятся так же, как любая другая команда (мост
  не различает их особо), чанки в пределах `VESC_BRIDGE_MAX_PAYLOAD`. Проверено на одной
  конфигурации (одна веска, одна модель) — на других моделях/версиях прошивки веск и других
  транспортах не проверялось. Длинный (3-байтный) вариант внешнего кадрирования (>65535 байт
  полезной нагрузки ОДНОГО пакета) не реализован.
- **`COMM_FW_VERSION`/`COMM_PING_CAN` (v1.9-1.10, `hw_type`/активный скан/QML-байты) и очередь
  форвардинга fire-and-forget (v1.11-1.12) — подтверждены на реальном VESC Tool 7.00** (сессия
  тестирования библиотеки). Прочие поля ответа на FW_VERSION (phase_filters/nrf флаги) по-прежнему
  всегда 0 — не проверялись, нужны ли конкретной версии VESC Tool.
- **Общий буфер пересборки ОТВЕТА (`can_rx_buf`), не пуловый по целевому ID.** С v1.12 форвардинг
  fire-and-forget — несколько запросов РАЗНЫМ целям могут быть в полёте одновременно (их CAN-кадры
  уже ушли, ответы ещё не пришли). Если ДВЕ РАЗНЫЕ вески одновременно пришлют многокадровые ответы
  (`FILL_RX_BUFFER[_LONG]`), их данные могут перемешаться в общем `can_rx_buf` и испортить оба ответа
  — на практике это не возникает, пока VESC Tool говорит ровно с ОДНОЙ веской за раз через вкладку
  CAN Fwd (её собственная модель), но при параллельном форвардинге НЕСКОЛЬКИМ целям одновременно
  (вне обычного сценария VESC Tool) это реальный риск, не решённый в этой версии.
- **Локальные команды сверх `COMM_FW_VERSION`/`COMM_PING_CAN`/`COMM_FORWARD_CAN`/
  `COMM_LISP_READ_CODE`/`COMM_GET_QML_UI_APP`/`COMM_CAN_FWD_FRAME` (см. §5) — мост молчит, КАК И
  настоящий Express** (`default: break` в его прошивке, подтверждено исходником) — это
  соответствие, не пробел.
- **Значение `send_flag = 0`** — см. §4, тоже кандидат на пересмотр, если форвардинг конкретных
  команд не получает ответа.
- **Конкурентный доступ к состоянию форвардинга.** `forward_src`/`forward_send_offset`/
  `forward_phase`/очередь пишутся и из контекста, откуда вызывается `VESC_Bridge_Tick()`/
  `VESC_Bridge_FeedBytes()` (может быть прерывание), и (с v1.12 УЖЕ НЕ из `VESC_Bridge_OnCanFrame()`
  — приём ответа полностью развязан с отправкой, см. "Очередь форвардинга" выше) — защищено
  раздельными короткими критическими секциями (`__disable_irq`/`__enable_irq`) вокруг каждого
  обращения к общему состоянию, НЕ одной секцией на всю функцию (см. @warning у
  `vesc_bridge_forward_step()` в `vesc_bridge.c` за подробным обоснованием именно такой разбивки).
- **Таймауты** `VESC_BRIDGE_FORWARD_TIMEOUT_MS` (по умолчанию 500 мс, с v1.12 влияет только на
  `VESC_Bridge_IsTargetActive()`, не на старт следующего форвардинга) — оценочное значение.
- **[v1.14] Таймаут разбора незавершённого входящего кадра — `VESC_Bridge_Config_t.rx_timeout_ms`**
  (0 = выключен; глобальный `VESC_BRIDGE_RX_TIMEOUT_MS` удалён). Для TCP/USB CDC (надёжный
  упорядоченный поток) ставьте 0 или >= 2000: пауза ≠ потеря байта, а сброс парсера посреди пакета
  превращал хвост в "мусор", в котором мог найтись 0x02/0x03, и СЛЕДУЮЩИЙ нормальный пакет
  проглатывался (фаззинг на реальном железе: ~3-4% серий при фрагментированной отправке, Windows
  ретранслирует потерянный TCP-сегмент через ~300 мс). Для UART — порядка 300 мс. Границу сессий
  обозначайте `VESC_Bridge_ResetRx()` при каждом новом подключении/обрыве клиента.
- **[v1.14] Ресинхронизация парсера:** при ошибке CRC/стоп-байта КОРОТКОГО кадра (<= 255 байт)
  принятые байты (кроме ложного старт-байта) перепрогоняются через парсер в поисках настоящего
  старта; для средних кадров (>255) по-прежнему просто отбрасываются.

## 8. Примеры подключения по транспорту

Модуль сам не знает про TCP/UART/USB — только два колбэка: `VESC_Bridge_FeedBytes()` (скормить
входящие байты) и `tx_callback` (сюда мост сам отдаёт исходящие байты). Общая часть кода одинакова
для всех сценариев:

**⚠️ [v1.13] Примеры ниже УПРОЩЕНЫ для читаемости — `tx_callback` в них дёргает транспорт
(`send()`/`HAL_UART_Transmit()`/`CDC_Transmit_FS()`) НАПРЯМУЮ, не оглядываясь на контекст вызова.**
Подтверждено тестированием на реальном железе: `tx_callback` для ответов вески вызывается ИЗ CAN RX
ПРЕРЫВАНИЯ (`VESC_Bridge_OnCanFrame()` диспетчеризуется `can_manager`-ом оттуда), даже если ваш
`VESC_Bridge_FeedBytes()` вызывается только из main. Блокирующий вызов из ISR (`HAL_UART_Transmit()`
с таймаутом 100 мс в примере ниже держал бы прерывания заблокированными до 100 мс при каждом ответе
вески) либо API, не рассчитанный на вызов из прерывания (lwIP `send()`/`tcp_write()`), — НЕБЕЗОПАСНЫ.
См. безопасный паттерн (кольцевой буфер в колбэке + отправка из main) в
[VESC_EXPRESS_GUIDE.md](VESC_EXPRESS_GUIDE.md) "Шаг 2" — используйте его вместо примеров ниже на
реальном проекте, здесь оставлено упрощённо ради компактности демонстрации самого API.

```c
#include "vesc_bridge.h"

static VESC_Bridge_t *s_bridge;

void BridgeInit(VESC_Bridge_TxCallback_t tx_callback, CANMGR_Handle_t *bus)
{
    VESC_Bridge_Config_t cfg = {
        .bus              = bus,      /* обычно та же шина, где зарегистрированы вески через VESC_CAN_Init() */
        .own_can_id       = 250,      /* НЕ должен совпадать ни с одной веской/мостом на этой шине! */
        .tx_callback      = tx_callback,
        .fw_version_major = 6,
        .fw_version_minor = 5,
        .hw_name          = "STM32-BRIDGE",
        .hw_type          = VESC_BRIDGE_HW_TYPE_CUSTOM_MODULE, /* хаб без своего мотора - см. §5 ниже */
    };
    s_bridge = VESC_Bridge_Init(&cfg);
}

void BridgeTick(void) { VESC_Bridge_Tick(s_bridge); } /* вызывать периодически (таймауты) */

/* Приём ответных CAN-кадров от весок - автоматический, через фильтр,
 * зарегистрированный VESC_Bridge_Init() в can_manager (см. §6) - никакого
 * VESC_CAN_OnForeignFrame() звать не нужно. */
```

### ПК (VESC Tool) → Ethernet → STM32 → CAN → veska

STM32 сам поднимает TCP-сервер (lwIP) на отдельном порту (у настоящего VESC Express это 65102):

```c
#include "lwip/sockets.h"

static int s_client_fd = -1;

static void bridge_tx_to_socket(VESC_Bridge_t *br, const uint8_t *data, uint16_t len)
{
    (void)br;
    if (s_client_fd >= 0) { send(s_client_fd, data, len, 0); }
}

/* Отдельная задача lwIP (например поверх FreeRTOS) - принимает ОДНО клиентское
   подключение и гоняет байты в обе стороны */
void BridgeNetworkTask(void *arg)
{
    (void)arg;
    BridgeInit(bridge_tx_to_socket);

    int listen_fd = socket(AF_INET, SOCK_STREAM, 0);
    /* ... bind()/listen() на нужном порту - как обычно в вашем стеке lwIP ... */

    for (;;)
    {
        s_client_fd = accept(listen_fd, NULL, NULL);
        uint8_t buf[512];
        int n;
        while ((n = recv(s_client_fd, buf, sizeof(buf), 0)) > 0)
        {
            VESC_Bridge_FeedBytes(s_bridge, buf, (uint16_t)n);
        }
        close(s_client_fd);
        s_client_fd = -1;
    }
}
```

`BridgeTick()` вызывайте из отдельного периодического таймера/задачи (независимо от
`BridgeNetworkTask`, которая блокируется на `recv()`).

### ПК → Ethernet → одноплатный компьютер → UART → STM32 → CAN → veska

Одноплатник (Raspberry Pi и т.п.) прозрачно перекладывает байты из своего TCP-сокета в UART и
обратно (например через `socat` или пару строк на Python) — STM32 вообще не знает, что "за UART" в
итоге сеть, для него это просто UART:

```c
static uint8_t s_uart_rx_byte;

void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart)
{
    if (huart->Instance == USART3)   /* UART, смотрящий на одноплатный компьютер */
    {
        VESC_Bridge_FeedBytes(s_bridge, &s_uart_rx_byte, 1U);
        HAL_UART_Receive_IT(huart, &s_uart_rx_byte, 1U); /* сразу готовим приём следующего байта */
    }
}

static void bridge_tx_to_uart(VESC_Bridge_t *br, const uint8_t *data, uint16_t len)
{
    (void)br;
    HAL_UART_Transmit(&huart3, (uint8_t *)data, len, 100);
}

void MainInit(void)
{
    BridgeInit(bridge_tx_to_uart);
    HAL_UART_Receive_IT(&huart3, &s_uart_rx_byte, 1U);
}
```

Приём по одному байту с `HAL_UART_Receive_IT` — самый простой вариант; для высокой нагрузки лучше
DMA в кольцевой буфер с вычиткой в `BridgeTick()`, `VESC_Bridge_FeedBytes()` одинаково хорошо
принимает и по байту, и большими кусками.

### ПК → Ethernet → одноплатный компьютер → USB Virtual COM Port → STM32 → CAN → veska

Со стороны STM32 это ровно тот же код, что и сценарий с USB VCP напрямую (ниже) — одноплатник для
STM32 неотличим от ПК, подключенного по USB напрямую. Разница целиком на стороне одноплатника (он же
и открывает `/dev/ttyACM0`, и слушает сеть).

### ПК (VESC Tool) → USB Virtual COM Port → STM32 → CAN → veska

STM32 поднимает USB CDC (Virtual COM Port) через штатный USB Device Middleware из CubeMX:

```c
/* CDC_Receive_FS - колбэк, сгенерированный CubeMX в usbd_cdc_if.c */
int8_t CDC_Receive_FS(uint8_t *Buf, uint32_t *Len)
{
    VESC_Bridge_FeedBytes(s_bridge, Buf, (uint16_t)*Len);
    USBD_CDC_ReceivePacket(&hUsbDeviceFS); /* сразу готовим приём следующего пакета */
    return USBD_OK;
}

static void bridge_tx_to_usb(VESC_Bridge_t *br, const uint8_t *data, uint16_t len)
{
    (void)br;
    CDC_Transmit_FS((uint8_t *)data, len);
}

void MainInit(void)
{
    BridgeInit(bridge_tx_to_usb);
}
```

Дальше в VESC Tool выбираете COM-порт (сценарии по USB) либо TCP-адрес STM32 (сценарий по Ethernet)
и работаете с вескими за мостом как с обычным CAN-устройством VESC Tool.
