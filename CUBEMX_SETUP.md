# Настройка CubeMX для motor_vesc

Периферию **CAN/FDCAN** целиком настраивает отдельная библиотека **can_manager**
(`can-managers-stm32`) — `motor_vesc`/`vesc_bridge` её не касаются вообще и собственных настроек
CubeMX для CAN/FDCAN не требуют. Полная таблица настроек CAN/FDCAN — README.md/API_REFERENCE.md
проекта `can-managers-stm32`.

Этот файл — про единственную периферию, которую `motor_vesc` использует НАПРЯМУЮ, в обход
can_manager: **RTC**, и только если включена опциональная функция "память положения" (см.
`VESC_CAN_SetPositionMemoryEnabled`/`VESC_CAN_SetCurrentPosition` в `motor_vesc.h`). Если эта функция
вам не нужна — ничего из этого файла настраивать не требуется, RTC-зависимый код в
`motor_vesc.c` в этом случае гейтится `#if defined(HAL_RTC_MODULE_ENABLED)` и компилируется в
безопасные заглушки (см. ниже).

`vesc_bridge.h` своих настроек CubeMX не требует сверх уже настроенной шины — сам транспорт (lwIP,
UART, USB CDC) настраивается отдельно, модуль о нём не знает.

---

## RTC — для функции "память положения"

### Зачем это нужно

Веска с датчиками Холла определяет положение вала только внутри одного электрического периода —
после выключения/включения питания самой вески абсолютная система координат (во внешнем смысле,
"откуда отсчитывать 0°") может "съехать": мотор физически не повернулся, а `pid_pos` на старте
показывает другое число. `motor_vesc` восстанавливает эту привязку силами STM32, сохраняя
скорректированное положение в **backup-регистры RTC** (домен VBAT) при каждом новом статусе
`STATUS_4` — дёшево (не флеш, ресурс перезаписи практически не ограничен) и доступно даже когда
основное питание платы снято, если на VBAT висит батарейка. Подробный разбор механики — секция
"Память положения между включениями вески" в `motor_vesc.h`.

### Что настроить в CubeMX

1. **Включить RTC** (`RCC` → в периферии включить RTC, либо сразу в дереве `Timers → RTC`).

2. **Источник тактирования RTC** — `RCC → RTC/AES Clock Source` (название вкладки отличается между
   сериями STM32, суть одна):

   | Значение | Когда выбирать | Компромисс |
   |---|---|---|
   | **LSE (внешний часовой кварц 32.768 кГц)** — рекомендуется | Если на плате уже разведён/можно развести кварц LSE | Точнее, переживает полное обесточивание платы ПРИ НАЛИЧИИ батареи на VBAT (см. ниже) — это единственный вариант, для которого честно подтверждена механика сохранения через полное снятие основного питания |
   | LSI (внутренний RC-генератор) | Если кварца LSE на плате нет и точность времени не важна (backup-регистрам она не важна вовсе — важно только то, что RTC тактируется и домен VBAT жив) | Менее точный, но для ЭТОЙ функции (backup-регистры, не само время) точность не используется — допустимо, если STM32 не обесточивается вместе с веской (тогда battery/VBAT persistence не нужна, см. ниже) |

   Для функции "память положения" точность хода часов НЕ используется вообще (библиотека не читает
   время/дату RTC, только пишет/читает backup-регистры) — выбор между LSE/LSI определяется ТОЛЬКО
   требованием к сохранению через полное обесточивание (см. следующий пункт), не точностью.

3. **Batterybacked домен (VBAT) — батарейка нужна, ТОЛЬКО если STM32 обесточивается ВМЕСТЕ с веской.**
   Backup-регистры RTC (домен VBAT) переживают сброс МК и переход в низкопотребляющие режимы
   ВСЕГДА, без всякой батареи. А вот переживание ПОЛНОГО обесточивания платы — только если на вывод
   VBAT заведена батарея (обычно CR2032 через диод, стандартная схема для RTC):
   - **STM32 питается постоянно, отдельно от вески** (типичный сценарий — отдельный источник питания
     логики) → батарея НЕ обязательна, backup-регистры и так переживут отключение вески.
   - **STM32 обесточивается вместе с веской** (одна цепь питания) → БЕЗ батареи на VBAT содержимое
     backup-регистров теряется при каждом полном отключении — функция "память положения" не
     сработает после такого отключения (отработает штатно только после сброса/сна МК, не после
     полного снятия питания).
   - Сам вывод VBAT, резистор/диод защиты и держатель батареи — вопрос схемотехники платы, не
     настройки CubeMX; CubeMX включает здесь только саму периферию RTC.

4. **Backup-регистры** (`RTC_BKP_DR0`, `RTC_BKP_DR1`, ...) в CubeMX НЕ настраиваются отдельно —
   доступны автоматически при включённом RTC. `motor_vesc` резервирует **ДВА ПОДРЯД идущих регистра**
   на КАЖДУЮ веску с включённой памятью положения (см. `VESC_Config_t.position_memory_backup_index`
   в `motor_vesc.h`) — разным вескам назначайте НЕПЕРЕСЕКАЮЩИЕСЯ индексы вручную, модуль это не
   проверяет (нет общего реестра занятых регистров между независимыми вызовами). Доступное
   количество регистров зависит от серии МК:

   | Серия | Регистров (`RTC_BKP_DR0`..) | Максимум весок с этой функцией |
   |---|---|---|
   | STM32F4 | 20 (0..19) | 10 |
   | STM32H7 | 32 (0..31) | 16 |

   (Для других серий — см. Reference Manual вашего МК, раздел RTC backup registers; число может
   отличаться.)

### Что НЕ входит в настройку CubeMX (ответственность приложения/библиотеки)

- `motor_vesc.c` сам вызывает `HAL_PWR_EnableBkUpAccess()` перед первой записью в backup-регистры —
  CubeMX для этого ничего дополнительно включать не нужно (это разрешение доступа к домену,
  программный вызов, не настройка периферии в `.ioc`).
- `HAL_RTC_Init()` должен быть УЖЕ выполнен (сгенерированным CubeMX кодом, как обычно) ДО первого
  `VESC_CAN_SetPositionMemoryEnabled()`/`VESC_CAN_SetCurrentPosition()` — `motor_vesc` RTC не
  инициализирует и не настраивает сама, только читает/пишет уже готовую периферию.
- Проект должен определять `HAL_RTC_MODULE_ENABLED` (CubeMX делает это сам при включении RTC в
  дереве периферии — проверять отдельно обычно не нужно, но если функция "молча" недоступна
  (`HAL_ERROR` от всех вызовов) — первое, что стоит проверить).

### Диагностика

| Симптом | Вероятная причина |
|---|---|
| `VESC_CAN_SetPositionMemoryEnabled()`/`SetCurrentPosition()` всегда возвращают `HAL_ERROR` | `HAL_RTC_MODULE_ENABLED` не определён (RTC не включён в CubeMX), либо `position_memory_hrtc` не задан в `VESC_Config_t` при `VESC_CAN_Init()` |
| Положение "съезжает" именно после полного обесточивания платы (но не после сброса/сна) | Нет батареи на VBAT, либо батарея разряжена/не подключена — см. пункт 3 выше |
| Две вески путают/перезаписывают друг другу сохранённое положение | Пересекающиеся `position_memory_backup_index` — см. пункт 4 выше, назначайте индексы вручную без пересечений |
