# motor_vesc

Портируемая C-библиотека для обмена с контроллерами электропривода **VESC** по шине **CAN / FDCAN** на микроконтроллерах **STM32**. Предназначена для встраиваемых систем, где нужно управлять несколькими VESC одновременно (колёсные приводы, роботизированные платформы, электротранспорт) быстро, неблокирующе и без ручного бит-баттлинга протокола.

| `vesc_bridge.h` / `vesc_bridge.c` | Опциональный мост VESC Tool ↔ CAN (аналог VESC Express) — поверх `motor_vesc.h`, добавляйте только если нужен удалённый доступ к вескам из VESC Tool. |

## Зачем нужна

VESC-контроллеры отдают телеметрию и принимают команды по CAN в виде однокадровых пакетов (скорость, ток, скважность и т.д.) и статусных пакетов (обороты, ток, температура, напряжение и др.). Реализовать это "с нуля" — разбор идентификаторов, масштабирование величин, очередь на переполнение буфера периферии, поддержку нескольких контроллеров и нескольких шин — рутинная и легко ошибающаяся работа. Библиотека берёт это на себя и предоставляет простой API: заполнил структуру конфигурации → получил хэндл → дальше просто вызываешь функции отправки команд и читаешь телеметрию из структуры.

## Поддерживаемые платформы

- **Любой STM32H7** и другие микроконтроллеры с периферией **FDCAN** (бэкенд выбирается автоматически по `HAL_FDCAN_MODULE_ENABLED`).
- **Любой STM32F4** и другие микроконтроллеры с классическим **bxCAN** (бэкенд выбирается автоматически по `HAL_CAN_MODULE_ENABLED`).
- Библиотека сама определяет доступный бэкенд на этапе компиляции — один и тот же код работает на обеих сериях без правок.
- Поддержка нескольких независимых CAN-шин одновременно (например, часть VESC на CAN1, часть — на CAN2 / FDCAN1 / FDCAN2).

## Основной функционал

- Регистрация произвольного числа VESC (лимит настраивается, по умолчанию 24 суммарно по всем шинам) через `VESC_CAN_Init()`.
- Отправка всех "простых" однокадровых команд протокола VESC: duty cycle, ток, тормозной ток, целевая скорость (эл. и механические RPM с учётом числа полюсов мотора), позиция, относительные варианты тока/тормоза, handbrake-ток.
- Неблокирующая отправка с программной очередью "на случай если аппаратный буфер периферии переполнен" и досылкой по кругу (round-robin) между всеми зарегистрированными VESC на шине — ни один контроллер не остаётся без команд надолго, даже под высокой нагрузкой на шину.
- Разбор полной телеметрии: обороты, ток, скважность, накопленные Ач/Втч, температуры FET и мотора, входной ток, позиция (PID), тахометр, входное напряжение, ADC-каналы, PPM — плюс кастомный статусный пакет с состоянием тормоза и произвольного цифрового датчика, подключённого к VESC.
- Кастомная (не входящая в официальный протокол VESC) команда однократного принудительного отпускания тормоза — `VESC_CAN_SendReleaseBrake()`, парная к соответствующему Lisp-скрипту на стороне вески.
- "Губернаторы" скорости и тока — программные (не встроенные в прошивку VESC) ограничители, которые действуют и напрямую на отправляемую команду, и "перекрёстно" по измеренной телеметрии (например: управляете током, но скорость не превышает заданный потолок).
- Память положения между включениями — сохранение скорректированного угла вала в backup-регистры RTC (battery-backed), чтобы после выключения и повторного включения VESC система координат не "съезжала".
- Callback-обработчик приёма ЛЮБОГО статусного пакета телеметрии (`VESC_CAN_SetTelemetryCallback`) — для немедленной реакции на приём данных не дожидаясь следующего опроса своего кода.
- Callback-обработчик кастомного цифрового датчика, подключённого к VESC — вызывается при получении соответствующего статуса.
- Программная имитация VESC (без физической шины) для отладки и разработки верхнеуровневой логики до подключения реального железа.
- Автоматическое обнаружение и восстановление после Bus-Off (единственная причина, по которой шина может "лечь" целиком у всех узлов сразу — см. "Честные ограничения") плюс счётчики Bus-Off/переполнений Rx FIFO для диагностики физических проблем шины — без этого требовалась перезагрузка МК.
- Транспорт-независимый мост VESC Tool ↔ CAN (`vesc_bridge.h`, аналог **VESC Express**) — позволяет открыть VESC Tool на ПК и настраивать/мониторить любую веску за STM32 так, будто в CAN-шину воткнут официальный VESC Express, по Ethernet, UART или USB Virtual COM Port — см. отдельный раздел ниже.

## Быстрый старт

1. Скопируйте [motor_vesc.h](motor_vesc.h) и [motor_vesc.c](motor_vesc.c) в свой проект CubeMX (папку с остальным пользовательским кодом, например `Core/Inc`/`Core/Src`). Нужен мост VESC Tool ↔ CAN — добавьте туда же [vesc_bridge.h](vesc_bridge.h)/[vesc_bridge.c](vesc_bridge.c) (зависит от motor_vesc.h, отдельно не работает). Файл [LICENSE](LICENSE) — по желанию, условия распространения уже в шапке каждого файла.
2. В CubeMX включите периферию **FDCAN** (STM32H7 и т.п.) либо **CAN** (STM32F4 и т.п.) и настройте битрейт под вашу CAN-сеть (обычно 500 кбит/с или 1 Мбит/с у VESC — должно совпадать у ВСЕХ узлов на шине). Библиотека сама настраивает приёмный фильтр — от CubeMX нужны только тактирование/Tx-Rx буферы/NVIC. Полный чек-лист (размер FIFO, какие именно прерывания NVIC включить для обоих бэкендов, включая обязательный `CANx_SCE_IRQn` для bxCAN) — в комментариях [motor_vesc.h](motor_vesc.h), секция "Что обязательно настроить в CubeMX заранее".
3. Сгенерируйте код в CubeMX, добавьте `#include "motor_vesc.h"` и код ниже ("Как использовать"). Соберите и прошейте как обычно.
4. Для доступа из VESC Tool к вескам через STM32 (аналог VESC Express) — доп. шаг, см. "Мост VESC Tool ↔ CAN" ниже.

Полный список функций API — [API_REFERENCE.md](API_REFERENCE.md); протокол моста и обоснование решений — [BRIDGE_PROTOCOL.md](BRIDGE_PROTOCOL.md).

## Как использовать

```c
#include "motor_vesc.h"

VESC_Handle_t *front_left;

void MotorsInit(void)
{
    VESC_Config_t cfg = {
        .hcan       = &hfdcan1,
        .vesc_id    = 10,
        .pole_count = 14,
    };
    front_left = VESC_CAN_Init(&cfg);
}

void ControlLoopTick(void)
{
    VESC_CAN_SendSpeed(front_left, 8000.0f);   /* электрические RPM */

    const VESC_Telemetry_t *t = &front_left->telemetry;
    float current = t->current;
    float temp    = t->temp_fet;
}
```

```c
/* Диспетчеризация приёма/отправки — вызывается из своих HAL callback-ов */
void HAL_FDCAN_RxFifo0Callback(FDCAN_HandleTypeDef *hfdcan, uint32_t RxFifo0ITs)
{
    VESC_CAN_RxFifo0_Handler(hfdcan, RxFifo0ITs);
}

void HAL_FDCAN_TxFifoEmptyCallback(FDCAN_HandleTypeDef *hfdcan)
{
    VESC_CAN_TxComplete_Handler(hfdcan);
}

/* Без этого обработчика шина не восстановится сама после Bus-Off - см. "Честные ограничения" */
void HAL_FDCAN_ErrorStatusCallback(FDCAN_HandleTypeDef *hfdcan, uint32_t ErrorStatusITs)
{
    VESC_CAN_ErrorStatus_Handler(hfdcan, ErrorStatusITs);
}
```

## Мост VESC Tool ↔ CAN (аналог VESC Express)

`vesc_bridge.h`/`vesc_bridge.c` — отдельный модуль поверх `motor_vesc.h`, реализующий доступ к веcкам за STM32 из VESC Tool на ПК так, будто в CAN-шину воткнут официальный **VESC Express**: STM32 разбирает протокол VESC Tool и форвардит команды нужной веске по CAN, а ответ пересылает обратно. Подробный протокол и обоснование решений — [BRIDGE_PROTOCOL.md](BRIDGE_PROTOCOL.md).

Модуль **транспорт-независим** — ничего не знает про TCP/UART/USB, только два колбэка: `VESC_Bridge_FeedBytes()` (скормить входящие байты) и `tx_callback` (сюда мост сам отдаёт исходящие байты). Поэтому один и тот же код моста работает без изменений в любом из сценариев:

```c
#include "vesc_bridge.h"

static VESC_Bridge_t *s_bridge;

/* Общая часть для ВСЕХ сценариев ниже */
void BridgeInit(VESC_Bridge_TxCallback_t tx_callback)
{
    VESC_Bridge_Config_t cfg = {
        .hcan             = &hfdcan1,     /* та же шина, на которой уже зарегистрированы вески через VESC_CAN_Init() */
        .own_can_id       = 250,          /* НЕ должен совпадать ни с одной веской/VESC Express на этой шине! */
        .tx_callback      = tx_callback,
        .fw_version_major = 6,
        .fw_version_minor = 5,
        .hw_name          = "STM32-BRIDGE",
    };
    s_bridge = VESC_Bridge_Init(&cfg);
}

/* Тоже общее для всех сценариев - вызывать периодически (таймауты) */
void BridgeTick(void) { VESC_Bridge_Tick(s_bridge); }

/* Тоже общее - подключаем приём ответов от весок по CAN */
void VESC_CAN_OnForeignFrame(VESC_CAN_HandleTypeDef *hcan, uint32_t ext_id,
                              const uint8_t *data, uint8_t len)
{
    (void)hcan; /* один мост - одна шина, hcan тут не нужен; при нескольких мостах сверяйте с VESC_Bridge_Config_t.hcan */
    VESC_Bridge_OnCanFrame(s_bridge, ext_id, data, len);
}
```

### 1) ПК (VESC Tool) → Ethernet → STM32 → CAN → veska

STM32 сам поднимает TCP-сервер (lwIP) на отдельном порту (у настоящего VESC Express это 65102) и работает с ним напрямую:

```c
#include "lwip/sockets.h"

static int s_client_fd = -1;

static void bridge_tx_to_socket(VESC_Bridge_t *br, const uint8_t *data, uint16_t len)
{
    (void)br;
    if (s_client_fd >= 0) { send(s_client_fd, data, len, 0); }
}

/* Отдельная задача lwIP (например поверх FreeRTOS) - принимает ОДНО клиентское
   подключение и гоняет байты в обе стороны */
void BridgeNetworkTask(void *arg)
{
    (void)arg;
    BridgeInit(bridge_tx_to_socket);

    int listen_fd = socket(AF_INET, SOCK_STREAM, 0);
    /* ... bind()/listen() на нужном порту - как обычно в вашем стеке lwIP ... */

    for (;;)
    {
        s_client_fd = accept(listen_fd, NULL, NULL);
        uint8_t buf[512];
        int n;
        while ((n = recv(s_client_fd, buf, sizeof(buf), 0)) > 0)
        {
            VESC_Bridge_FeedBytes(s_bridge, buf, (uint16_t)n);
        }
        close(s_client_fd);
        s_client_fd = -1;
    }
}
```

`BridgeTick()` вызывайте из отдельного периодического таймера/задачи (независимо от `BridgeNetworkTask`, которая блокируется на `recv()`).

### 2) ПК → Ethernet → одноплатный компьютер → UART → STM32 → CAN → veska

Одноплатник (Raspberry Pi и т.п.) прозрачно перекладывает байты из своего TCP-сокета в UART и обратно (например через `socat` или пару строк на Python) — STM32 вообще не знает, что "за UART" в итоге сеть, для него это просто UART:

```c
static uint8_t s_uart_rx_byte;

void HAL_UART_RxCpltCallback(UART_HandleTypeDef *huart)
{
    if (huart->Instance == USART3)   /* UART, смотрящий на одноплатный компьютер */
    {
        VESC_Bridge_FeedBytes(s_bridge, &s_uart_rx_byte, 1U);
        HAL_UART_Receive_IT(huart, &s_uart_rx_byte, 1U); /* сразу готовим приём следующего байта */
    }
}

static void bridge_tx_to_uart(VESC_Bridge_t *br, const uint8_t *data, uint16_t len)
{
    (void)br;
    HAL_UART_Transmit(&huart3, (uint8_t *)data, len, 100);
}

void MainInit(void)
{
    BridgeInit(bridge_tx_to_uart);
    HAL_UART_Receive_IT(&huart3, &s_uart_rx_byte, 1U);
}
```

Приём по одному байту с `HAL_UART_Receive_IT` — самый простой вариант; для высокой нагрузки лучше DMA в кольцевой буфер с вычиткой в `BridgeTick()`, `VESC_Bridge_FeedBytes()` одинаково хорошо принимает и по байту, и большими кусками.

### 3) ПК → Ethernet → одноплатный компьютер → USB Virtual COM Port → STM32 → CAN → veska

Со стороны STM32 это **ровно тот же код, что и сценарий 4** ниже (VCP) — одноплатник для STM32 неотличим от ПК, подключенного по USB напрямую. Разница целиком на стороне одноплатника (он же и открывает `/dev/ttyACM0`, и слушает сеть).

### 4) ПК (VESC Tool) → USB Virtual COM Port → STM32 → CAN → veska

STM32 поднимает USB CDC (Virtual COM Port) через штатный USB Device Middleware из CubeMX:

```c
/* CDC_Receive_FS - колбэк, сгенерированный CubeMX в usbd_cdc_if.c */
int8_t CDC_Receive_FS(uint8_t *Buf, uint32_t *Len)
{
    VESC_Bridge_FeedBytes(s_bridge, Buf, (uint16_t)*Len);
    USBD_CDC_ReceivePacket(&hUsbDeviceFS); /* сразу готовим приём следующего пакета */
    return USBD_OK;
}

static void bridge_tx_to_usb(VESC_Bridge_t *br, const uint8_t *data, uint16_t len)
{
    (void)br;
    CDC_Transmit_FS((uint8_t *)data, len);
}

void MainInit(void)
{
    BridgeInit(bridge_tx_to_usb);
}
```

Дальше в VESC Tool выбираете COM-порт (сценарии 3-4) либо TCP-адрес STM32 (сценарий 1) и работаете с вескими за мостом как с обычным CAN-устройством VESC Tool.

## Требования

- STM32 HAL с включённым `HAL_FDCAN_MODULE_ENABLED` либо `HAL_CAN_MODULE_ENABLED`.
- Для памяти положения — включённый `HAL_RTC_MODULE_ENABLED` и проинициализированный в CubeMX RTC (для сохранения через полное обесточивание платы дополнительно нужна батарея на выводе VBAT).
- Для моста (`vesc_bridge.h`) — только `motor_vesc.h`/`motor_vesc.c` (хотя бы одна веска уже зарегистрирована через `VESC_CAN_Init()` на нужной шине). Сам транспорт (lwIP, UART, USB CDC) — целиком на вас, модуль о нём не знает.

## Что реально проверено

- Библиотека и весь код примеров из этого README собираются и линкуются без предупреждений (`-Wall -Wextra`) под `STM32H743xx` (FDCAN) и `STM32F446xx` (bxCAN), с памятью положения включённой и выключенной.
- CRC16 и формат внешнего кадрирования моста (см. `BRIDGE_PROTOCOL.md` §2) численно сверены с эталонным контрольным вектором CRC-16/XMODEM.
- **Не проверялось на реальном железе** — электрическое поведение шины, реальный обмен с VESC Tool и реакция реальных весок остаются неподтверждёнными. См. "Честные ограничения" ниже.

## Честные ограничения

- Отправка полного набора команд конфигурации VESC (через `COMM_SET_MCCONF_TEMP` и аналогичные) не реализована — библиотека работает только с "простыми" однокадровыми командами протокола CAN.
- Точная внутренняя семантика команды `SET_CURRENT_HANDBRAKE` в прошивке VESC документально не подтверждена — для задач принудительного удержания вала рекомендуется `VESC_CAN_SendCurrentBrake()`.
- Управление по скорости (`VESC_CAN_SendSpeed`/`SendMechanicalSpeed`) само по себе реализовано и проверено корректно, но результат зависит от настроек самой вески в VESC Tool (Speed PID, Minimum ERPM) — см. предупреждение у `VESC_CAN_SendSpeed` в `motor_vesc.h`.
- "Шина легла целиком, все VESC разом, само не восстанавливается" — по протоколу CAN это ВСЕГДА Bus-Off (единственный такой механизм), а Bus-Off — ВСЕГДА следствие реальных ошибок кадров (несовпадающий битовый тайминг между узлами, неисправный/не тот узел на шине, отсутствующий/лишний терминатор, наводки), никогда — просто объёма корректного трафика. Библиотека теперь обнаруживает и автоматически восстанавливается после Bus-Off (`VESC_CAN_ErrorStatus_Handler`, см. выше) — но это лечит симптом (связь возобновляется), а не причину: если `VESC_CAN_GetBusOffCount()` продолжает расти, ищите физическую/конфигурационную проблему на самой шине.
- Мост VESC Tool ↔ CAN (`vesc_bridge.h`) рассчитан на конфигурационные команды, не на обновление прошивки весок через мост; часть протокола (ответ на `COMM_FW_VERSION`, `COMM_PING_CAN`, значение флага `send` при форвардинге) реализована по наиболее достоверной трактовке исходников VESC, но не проверялась на реальном стенде — полный честный разбор и что поправить в первую очередь — [BRIDGE_PROTOCOL.md](BRIDGE_PROTOCOL.md).
