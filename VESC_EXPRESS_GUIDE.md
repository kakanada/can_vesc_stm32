# Как использовать мост в роли VESC Express

Практическое руководство "от задачи, а не от протокола": как подключить `vesc_bridge` так, чтобы
VESC Tool на ПК видел STM32 как CAN-хаб (аналог официального **VESC Express**) и настраивал реальные
вески за ним по CAN. Для построчного разбора протокола, байтов кадров и истории решений — см.
[BRIDGE_PROTOCOL.md](BRIDGE_PROTOCOL.md); для остального API библиотеки — [API_REFERENCE.md](API_REFERENCE.md).

Статус на 01.10.2026: `vesc_bridge` v1.13, полный набор тестов (40/40, включая конвейер запросов,
realtime-поток 60 с, запись MCCONF/APPCONF с побайтовой сверкой, переподключения, повреждённые
кадры) пройден на реальном VESC Tool 7.00 (сессия тестирования библиотеки, проект
`F:\1_1_stm32h743vit6_test_library`, TCP-порт 65102 поверх `usb_eth`).

---

## 1. Что это даёт и когда это нужно

VESC Tool умеет разговаривать с веской либо напрямую (USB/UART), либо через "CAN-хаб" — устройство,
которое само на CAN-шине, а с VESC Tool общается по своему каналу (USB/UART/**TCP** — именно TCP
используется, если хаб висит в IP-сети). Официальная реализация такого хаба — **VESC Express**
(ESP32 с собственной прошивкой). Эта библиотека (`vesc_bridge.h`/`vesc_bridge.c`) — программная
реализация ТОЙ ЖЕ роли на STM32 поверх уже работающей CAN-периферии (`can_manager`): VESC Tool
подключается к STM32 по вашему транспорту, STM32 разбирает протокол, форвардит команды веске нужным
CAN ID и пересылает ответ обратно.

Нужно это, если вы хотите настраивать/мониторить реальные вески на шине удалённо через VESC Tool, не
подключая кабель USB к каждой веске физически. Если вам нужно только управлять моторами из своего
кода — это `motor_vesc.h`, мост не требуется вовсе.

---

## 2. Пошаговая интеграция

### Шаг 0 — предпосылки

- `can_manager` уже инициализирован на нужной шине (`CANMGR_Init()`), периферия CAN/FDCAN настроена
  и запущена — мост сам периферией не владеет (см. "Зависимость от can_manager" в
  `BRIDGE_PROTOCOL.md` §6).
- **⚠️ В CubeMX для FDCAN ОБЯЗАТЕЛЬНО включён Auto Retransmission**
  (`hfdcan.Init.AutoRetransmission = ENABLE`, в CubeMX: FDCAN1 → Parameter Settings → Auto
  Retransmission). Подтверждённая на реальном железе находка: по умолчанию CubeMX ставит `DISABLE` —
  кадр, проигравший арбитраж шины (а он ПРОИГРЫВАЕТ регулярно, когда веска одновременно шлёт свой
  статус/ответ), аппаратно ОТМЕНЯЕТСЯ НАВСЕГДА (виден в `TXBCF` - Tx Buffer Cancellation Finished) и
  запрос мостом "теряется" МОЛЧА, без какой-либо ошибки в самой библиотеке — при пачке из 5
  форвардированных запросов отвечало 1-3. С `ENABLE` — 5 из 5 при любом интервале. См. также
  "Диагностика" ниже.
- Число фильтров CAN/FDCAN в CubeMX (`StdFiltersNbr`/`ExtFiltersNbr` для FDCAN) — НЕ МЕНЬШЕ, чем
  суммарно регистрирует `motor_vesc`+`vesc_bridge` на этой шине (5 точных фильтров только у моста,
  см. `VESC_Bridge_Init()`, плюс фильтры motor_vesc, если вески тоже зарегистрированы через
  `VESC_CAN_Init()`) — иначе часть регистраций фильтров молча отклоняется (`CANMGR_RegisterFilter()`
  возвращает ошибку — ПРОВЕРЯЙТЕ возврат `VESC_Bridge_Init()`/`VESC_CAN_Init()`, не игнорируйте
  `NULL`), и соответствующие кадры никогда не доходят до библиотеки на уровне периферии.
- Скорость шины (битрейт) STM32 совпадает со скоростью, настроенной в самой веске (VESC Tool → App
  Settings → General → CAN Baud Rate) — обычно 500 кбит/с, но стоит сверить, а не предполагать.
- У вас есть ЛЮБОЙ байтовый транспорт PC ↔ STM32: TCP-сервер (lwIP), UART или USB CDC VCP — мост
  транспорт-независим, ему нужны только два колбэка (см. шаг 2).
- Выбран `own_can_id` моста — ЛЮБОЙ ID, НЕ совпадающий ни с одной реальной веской и ни с одним другим
  устройством на этой шине (библиотека это не проверяет — ответственность вызывающего кода, как и
  `position_memory_backup_index` в `motor_vesc.h`). Конкретное число (например 100 или 250 в примерах
  ниже) значения не имеет — важна только уникальность на вашей конкретной шине; не полагайтесь на
  то, что какой-то диапазон "зарезервирован" — у вас может быть несколько весок/мостов/иных устройств
  с произвольными ID.

### Шаг 1 — заполнить `VESC_Bridge_Config_t`

```c
#include "vesc_bridge.h"

static uint8_t s_bridge_uuid[12] = { 0xDE, 0xAD, 0xBE, 0xEF, 0, 0, 0, 0, 0, 0, 0, 0x01 };

VESC_Bridge_Config_t cfg = {
    .bus               = bus,                              /* CANMGR_Handle_t*, см. can_manager.h */
    .own_can_id        = 250,                               /* НЕ должен совпадать ни с одной веской/мостом! */
    .tx_callback       = BridgeTxCallback,                   /* см. шаг 2 */
    .fw_version_major  = 6,
    .fw_version_minor  = 5,
    .hw_name           = "STM32-H743-HUB",                   /* до 31 символа */
    .hw_type           = VESC_BRIDGE_HW_TYPE_CUSTOM_MODULE,   /* КРИТИЧНО - см. предупреждение ниже */
    .custom_config_num = 0,
    .uuid12            = s_bridge_uuid,                       /* либо NULL - 12 нулевых байт */
    .fw_name           = "stm32-vesc-bridge",                 /* до 31 символа, опционально */
    .rx_timeout_ms     = 0,                                   /* TCP/USB CDC: 0; UART: ~300 - см. шаг 2 / v1.14 */
};
VESC_Bridge_t *bridge = VESC_Bridge_Init(&cfg);
```

**⚠️ `hw_type = VESC_BRIDGE_HW_TYPE_CUSTOM_MODULE` обязателен для роли хаба.** Значение по умолчанию
(`VESC_BRIDGE_HW_TYPE_VESC`, оставлено ради обратной совместимости со старым кодом) заставляет VESC
Tool считать STM32 ОБЫЧНОЙ веской — он тогда пытается прочитать MCCONF/APPCONF МОТОРА у самого моста
(которого у хаба нет и быть не должно), UI остаётся пустым/в ошибке, а до реальной вески за мостом
(вкладка CAN Fwd) пользователь не добирается интуитивно. Это подтверждённая на реальном железе
находка (см. `BRIDGE_PROTOCOL.md` §5) — не теоретическое предостережение.

### Шаг 2 — подключить транспорт (два колбэка)

**⚠️ `tx_callback` вызывается из CAN RX прерывания, не только из main.** Ответы вески приходят через
`VESC_Bridge_OnCanFrame()`, которая диспетчеризуется `can_manager`-ом ИЗ ПРЕРЫВАНИЯ приёма CAN
(`CANMGR_RxFifo_Handler`) — `tx_callback` для этих ответов вызывается ПРЯМО ОТТУДА, даже если
`VESC_Bridge_FeedBytes()` вы сами вызываете только из основного цикла. Подтверждённая тестированием
на реальном железе ошибка: прямой вызов блокирующего/не ISR-safe API транспорта (например
`tcp_write()`/`tcp_output()` lwIP) ПРЯМО ИЗ `tx_callback` небезопасен — стек lwIP на это не
рассчитан. Правильный паттерн — колбэк копирует байты в свой кольцевой буфер и сразу возвращается,
реальная отправка в транспорт — из основного цикла:

```c
/* 1) STM32 -> VESC Tool: мост сам зовёт это, когда есть что отправить -
 * ВОЗМОЖНО ИЗ CAN RX ПРЕРЫВАНИЯ (см. ⚠️ выше) - колбэк должен быть быстрым
 * и НЕ дёргать транспорт напрямую. */
static void BridgeTxCallback(VESC_Bridge_t *br, const uint8_t *data, uint16_t len)
{
    uint32_t primask = __get_PRIMASK();   /* save/restore, НЕ безусловный __enable_irq() - см.
                                            * @warning у vesc_bridge_forward_step() в vesc_bridge.c
                                            * за тем, почему это важно при вложенных критических секциях */
    __disable_irq();
    ring_buffer_push(&s_tx_ring, data, len);   /* ваша реализация - копирует байты, не блокирует */
    __set_PRIMASK(primask);
}

/* Из основного цикла - опустошает кольцевой буфер в реальный транспорт. */
void MainLoopTxPump(void)
{
    uint8_t  chunk[256];
    uint16_t chunk_len;
    while (ring_buffer_pop(&s_tx_ring, chunk, sizeof(chunk), &chunk_len) && (chunk_len > 0U))
    {
        tcp_write(s_client_pcb, chunk, chunk_len, TCP_WRITE_FLAG_COPY);
    }
    tcp_output(s_client_pcb);
}

/* 2) VESC Tool -> STM32: вызывайте из своего приёма (TCP recv callback,
 * UART RX прерывание/DMA, USB CDC receive) - байт сколько угодно за раз. */
void OnBytesFromClient(const uint8_t *data, uint16_t len)
{
    VESC_Bridge_FeedBytes(bridge, data, len);
}
```

Этот же паттерн (кольцевой буфер в `tx_callback` + отправка из главного цикла) используется в
тестовом стенде (`test_library/Core/Src/vesc_link.c`) и прошёл полный набор тестов на реальном
железе. Готовые примеры под lwIP TCP-сервер, UART, USB CDC VCP и связку "Ethernet → одноплатный ПК →
UART/USB → STM32" — README.md ("Мост VESC Tool ↔ CAN") и `BRIDGE_PROTOCOL.md` §8 (упрощены для
читаемости — на реальном lwIP-транспорте применяйте паттерн выше, а не прямой вызов `tcp_write` из
колбэка).

### Шаг 3 — периодическое обслуживание

```c
void MainLoopOrTimer(void) { VESC_Bridge_Tick(bridge); } /* раз в несколько десятков мс достаточно */
```

Дренирует очередь форвардинга и чистит таймауты парсера входящих байт (см. §4 ниже про таймауты).

### Шаг 4 — TCP-порт

Протокол VESC Tool не завязан на конкретный порт — используйте любой свободный. В протестированном
стенде использован **65102** (поверх USB-Ethernet адаптера на STM32, адрес хаба `192.168.7.1`) —
просто пример, не требование библиотеки. В VESC Tool: вкладка подключения → **TCP** → IP и порт
вашего моста.

### Шаг 5 — подключение из VESC Tool

1. VESC Tool → Connect → TCP → ввести IP:порт моста.
2. После подключения мост отвечает на `COMM_FW_VERSION` как `hw_type = CUSTOM_MODULE` — VESC Tool
   показывает хаб, не веску.
3. Вкладка **CAN Fwd** (или аналогичная в вашей версии VESC Tool) → **Scan** — мост выполняет
   активный скан шины (`CAN_PACKET_PING` по всем ID, см. `BRIDGE_PROTOCOL.md` §5) и возвращает список
   реально ответивших ID (~150-200 мс).
4. Выбрать нужный ID из списка — дальше VESC Tool обычным образом читает/пишет MCCONF/APPCONF,
   показывает телеметрию и т.п. — всё это форвардится мостом на выбранный CAN ID прозрачно.

## 3. Какие команды мост обрабатывает САМ, какие форвардит

| Команда (COMM_PACKET_ID) | Обрабатывается | Что происходит |
|---|---|---|
| `COMM_FORWARD_CAN` (34) | мостом | достаёт целевой CAN ID + вложенную команду, форвардит по CAN (см. `BRIDGE_PROTOCOL.md` §3-4) — это ОСНОВНОЙ канал всего общения с реальными весками |
| `COMM_FW_VERSION` (0) | мостом локально | идентификация самого хаба (см. шаг 1 выше) |
| `COMM_PING_CAN` (62) | мостом локально | активный скан шины (CAN ID 0..254), см. §5 |
| `COMM_LISP_READ_CODE` (130), `COMM_GET_QML_UI_APP` (118) | мостом локально | пустой ответ ("скрипта/QMLUI нет") — байты сверены с прошивкой настоящего VESC Express |
| `COMM_CAN_FWD_FRAME` (33) | мостом локально | отправка одного "сырого" CAN-кадра по явному ID (отладка/CAN-анализатор в VESC Tool) |
| всё остальное, адресованное веске (`COMM_GET_MCCONF`, `COMM_SET_MCCONF`, `COMM_GET_VALUES`, `COMM_GET_APPCONF`, терминал и т.п.) | веской, через форвардинг | VESC Tool сам заворачивает их в `COMM_FORWARD_CAN` после выбора цели — мост не разбирает их содержимое, прозрачно пересылает |
| любая другая локальная команда (не адресованная веске) | мост молчит | ТОЧНО как настоящий VESC Express (`default: break` в его прошивке) — это соответствие, не пробел, см. `BRIDGE_PROTOCOL.md` §5 |

Форвардинг с v1.12 — **fire-and-forget**: мост не ждёт ответа вески, чтобы начать следующий
запрос (так же, как настоящий VESC Express) — ответы приходят асинхронно и пересылаются VESC Tool по
мере получения. Запросы ставятся в очередь (`VESC_BRIDGE_FORWARD_QUEUE_BYTES`, см.
`vesc_bridge.h`) — см. `BRIDGE_PROTOCOL.md` §3 за подробностями и диагностикой переполнения.

## 4. Ограничения и честные компромиссы

Полный список — `BRIDGE_PROTOCOL.md` §7, здесь — то, что важно знать ПЕРЕД развёртыванием:

- **Обновление прошивки весок через мост проверено на реальном VESC Tool 7.00** (веска hw 410, fw 7.0;
  STM32H743, FDCAN 500 кбит/с, AutoRetransmission=ENABLE, vesc_bridge 1.13, TCP 65102 поверх
  usb_eth) — прошло успешно, веска после этого работает. На других моделях/версиях веск и транспортах
  не проверялось. См. `BRIDGE_PROTOCOL.md` §7.
- **Общий буфер пересборки ответа.** Если VESC Tool говорит ровно с одной веской за раз (штатный
  сценарий CAN Fwd) — проблем нет. Параллельный форвардинг НЕСКОЛЬКИМ целям одновременно (вне
  обычного сценария VESC Tool) рискует перемешать многокадровые ответы разных весок.
- **Увеличивайте `VESC_BRIDGE_FORWARD_QUEUE_BYTES`, если часто пишете большие конфигурационные
  пакеты (SET_MCCONF/APPCONF) и видите рост `VESC_Bridge_GetForwardQueueOverflowCount()`.** Имейте в
  виду: симптом "очередь переполняется"/"веска не успевает" может на деле означать отключённый
  `AutoRetransmission` (см. "Диагностика" ниже) — кадры физически теряются на шине, а не "не успевают
  влезть в очередь"; сначала исключите это, прежде чем просто увеличивать размер очереди.
- **Таймауты не измерялись под реальной нагрузкой вашей сети/шины** — `VESC_BRIDGE_FORWARD_TIMEOUT_MS`
  (только для `VESC_Bridge_IsTargetActive()`, с v1.12 не блокирует форвардинг) и
  оценочное значение.
- **[v1.14] `rx_timeout_ms` (поле `VESC_Bridge_Config_t`, 0 = выключен) и `VESC_Bridge_ResetRx()`.**
  Для TCP/USB CDC ставьте `rx_timeout_ms = 0` (или >= 2000) — пауза в потоке не означает потерю байта
  (TCP ретранслирует потерянный сегмент, Windows ~300 мс), а сброс парсера по таймауту ломал разбор
  СЛЕДУЮЩЕГО пакета (~3-4% серий при фрагментированной отправке). Для UART — около 300 мс. При
  каждом НОВОМ подключении клиента / обрыве вызывайте `VESC_Bridge_ResetRx(bridge)` (иначе
  недочитанный пакет прошлой сессии съест начало первого пакета новой). Ошибка CRC/стопа короткого
  кадра теперь ресинхронизируется (поиск старт-байта внутри уже принятого).
- **`own_can_id`/`VESC_Config.pole_count`-подобная ответственность вызывающего кода** — библиотека не
  проверяет уникальность CAN ID моста на шине.

## 5. Диагностика типичных симптомов

| Симптом | Вероятная причина | Что проверить |
|---|---|---|
| VESC Tool подключается, но видит хаб как обычную веску, читает пустой/ошибочный MCCONF у самого моста | `hw_type` не `VESC_BRIDGE_HW_TYPE_CUSTOM_MODULE` | Шаг 1 выше |
| STM32 вообще не принимает кадры с шины (`RXF0S`/счётчик приёма = 0), хотя TX подтверждается | RX-пин FDCAN неверно замаплен/перепутан с TX, либо `StdFiltersNbr`/`ExtFiltersNbr` в CubeMX меньше реально регистрируемых фильтров | Шаг 0 выше; проверьте возврат `VESC_CAN_Init()`/`VESC_Bridge_Init()` |
| При пачке из нескольких форвардированных запросов отвечает только часть (1-3 из 5), остальные "теряются" без ошибки в логах | **`AutoRetransmission = DISABLE` в CubeMX** — кадр, проигравший арбитраж шины, аппаратно отменяется навсегда | Шаг 0 выше — включите `AutoRetransmission`. С `can_manager` ≥ v0.6 `CANMGR_Init()` сам логирует `LOG_CODE_CANMGR_NO_AUTORETRANS` при опциональной интеграции со `stm32_logger` (не блокирует инициализацию) — см. README.md `can-managers-stm32` |
| Периодически приходит повреждённый/с неверным CRC внешний кадр от STM32 к VESC Tool (редко, под нагрузкой realtime-опроса + локальных команд одновременно) | До v1.13 — общий буфер сборки кадра между CAN RX ISR и main-контекстом (см. `BRIDGE_PROTOCOL.md` §3, "гонка tx_frame_buf") | Обновитесь до v1.13+ (раздельные буферы `tx_frame_buf`/`tx_frame_buf_isr`) |
| Зависания/крэши стека транспорта (lwIP и т.п.) при обмене с веской, особенно под нагрузкой | `tx_callback` дёргает не-ISR-safe API транспорта напрямую, а вызывается он может быть из CAN RX прерывания | Шаг 2 выше — кольцевой буфер + PRIMASK save/restore в колбэке, отправка из main |
| `VESC_Bridge_GetForwardQueueOverflowCount()` растёт | Очереди не хватает при реальном темпе VESC Tool, ЛИБО (что проверить в первую очередь) веска не успевает из-за потерь кадров на шине | Проверьте `AutoRetransmission` ПЕРЕД тем, как просто увеличивать `VESC_BRIDGE_FORWARD_QUEUE_BYTES` |
| `VESC_Bridge_GetRxErrorCount()`/`GetCanCrcErrorCount()` растут | Шум на линии транспорта / потеря CAN-кадров при пересборке многокадрового ответа | См. `CANMGR_GetBusOffCount()`/`GetRxOverflowCount()` в `can_manager.h` — вероятная связанная причина |

## 6. Безопасность

- Мост — ПРОЗРАЧНАЯ труба к управлению реальными моторами по CAN. Любой, кто может подключиться к
  вашему транспорту (TCP-порту, если он доступен снаружи локальной сети), получает ПОЛНЫЙ доступ к
  настройке и управлению всеми вескaми на шине — ровно так же, как физическое подключение VESC Tool
  напрямую. Протокол сам по себе НЕ содержит аутентификации — это аналогично официальному VESC
  Express, не особенность этой реализации.
- Если транспорт — TCP поверх Wi-Fi/Ethernet, ограничивайте доступ на уровне сети (отдельный
  VLAN/подсеть, файрвол, не выставляйте порт в интернет напрямую).
- `COMM_CAN_FWD_FRAME` (см. §3 выше) позволяет отправить ПРОИЗВОЛЬНЫЙ CAN-кадр на ЛЮБОЙ ID шины в
  обход адресации `(cmd_id<<8)|vesc_id` остального протокола — то же самое, что умеет настоящий VESC
  Express (используется его встроенным CAN-анализатором), но стоит понимать степень доступа, которую
  это даёт тому, кто подключился к мосту.
- `VESC_CAN_SendCustomCommand()`/кастомные статусы (`motor_vesc.h`) используют тот же диапазон кодов
  команд, что и форвардинг — выбирайте коды, заведомо не пересекающиеся с официальным протоколом VESC
  (см. предупреждения в `motor_vesc.h`), чтобы форвардинг через мост случайно не попал на ваш
  кастомный обработчик (и наоборот).

## 7. Как тестировать

1. **Синтаксическая/логическая проверка без железа** — компиляция (`arm-none-eabi-gcc -fsyntax-only`
   с минимальным стабом `can_manager.h`) ловит опечатки/несовпадение типов, но не проверяет реальный
   протокол — обязательно нужен шаг 2 или 3 ниже перед тем, как полагаться на новую версию.
2. **Эмулятор VESC Tool** — тестовая сессия использует Python/PowerShell-скрипт
   (`vesctool_sim.ps1`/`vesctool_suite.ps1` в проекте `F:\1_1_stm32h743vit6_test_library`), который
   воспроизводит реальные последовательности запросов VESC Tool (включая конвейерные/некорректные
   сценарии) и byte-for-byte сверяет ответ. Это основной способ ловить протокольные баги БЕЗ
   настоящего VESC Tool под рукой — именно так найдены баги с QML-байтами (v1.10) и
   fire-and-forget форвардингом (v1.12).
3. **Настоящий VESC Tool** — финальная проверка перед тем, как считать версию готовой: подключение,
   скан шины, чтение И ЗАПИСЬ конфигурации (не только чтение — баг с конвейерным форвардингом v1.11
   проявлялся именно на записи), работа с реальной нагрузкой на шине (не только одна тестовая веска).

Если вы меняете `vesc_bridge.c`/`.h` — после смены сверяйтесь с исходником прошивки
`vedderb/vesc_express` (`main/commands.c`) для любого протокольного поведения, которое не покрыто
существующими тестами: это тот же метод, которым найдены все протокольные правки с v1.9 по v1.12 —
не угадывание байтов, а чтение авторитетного источника.
